# План тестирования первого этапа

Объект: REST-сервис ветки `simple-student`, FastAPI + SQLAlchemy + PostgreSQL.
Основание: персональное ТЗ и пп. 2.7.5, 2.8.6 методических рекомендаций 2026.
Цель: проверить обязательные функции, права, ошибки и форматы файлов.
Django, UI-формы второго этапа, нагрузочные испытания и эксплуатационная
устойчивость не входят в этот этап проверки.

## Среда и данные

Python 3.12, PostgreSQL 17 как обычная служба, зависимости из
`requirements-dev.txt`. `TEST_DATABASE_URL` указывает на отдельную базу с суффиксом
`_test`. Каждая проверка выполняется в откатываемой транзакции; файлы временные.
Фикстуры создают администратора, двух преподавателей, двух студентов и олимпиаду
на сегодня. Для проверки объёма данных отдельно вызывается `seed_demo` в пустой
тестовой транзакции: по 50 записей и 50 настоящих файлов Word. Исходные реальные
персональные данные не используются.

Тестовые файлы создаются в памяти: корректные DOCX/XLSX средствами библиотек;
TXT — UTF-8; неправильные PDF/PNG/JPG/DOCX — заведомо неверные байты; большой
TXT — 5 МБ + 1 байт. См. таблицу данных в [TEST_CASES.md](TEST_CASES.md).

## Стратегия и порядок

1. Проверить доступность отдельной PostgreSQL и установить зависимости.
2. Проверить хеши паролей и JWT, затем роли и создание пользователей.
3. Проверить CRUD, списки v1/v2 и ограничения параметров.
4. Выполнить связанный сценарий: заявка → баллы → подготовка → отзыв → публикация.
5. Проверить документы, их замену и чтение настоящих Word/Excel.
6. Проверить наполнение, повторную инициализацию, регрессию и покрытие.
7. Повторить основной сценарий через работающий Uvicorn, зафиксировать результаты.

Применяются модульные проверки хеширования, функциональные API-тесты,
интеграционные проверки с настоящей PostgreSQL, негативные и граничные проверки,
сравнение версий и регрессия. Для обязательных дополнений сначала выполнены
падающие тесты на отсутствующие операции, затем внесена реализация и выполнен
повторный прогон. Применение TDD ко всей предшествующей истории не заявляется.

Критерии начала: доступны код, зависимости и тестовая БД; определены поля и роли.
Критерии окончания: все выбранные тесты прошли, нет известных блокирующих
функциональных дефектов, покрытие маршрутов и общего кода `app` не ниже 80%,
файлы отчётов повторно открываются. Порог `--cov-fail-under=80` задан в `pytest.ini`.
